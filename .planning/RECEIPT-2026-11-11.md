## 1. 环境前置（不看必踩）

编译后端（CGO + DuckDB）**必须**用 GCC 15，否则回到链接失败：

```powershell
$env:PATH = 'D:\tools\gcc15\mingw64\bin;' + $env:PATH
$env:CC   = 'D:\tools\gcc15\mingw64\bin\gcc.exe'
$env:CXX  = 'D:\tools\gcc15\mingw64\bin\g++.exe'
gcc --version     # 必须 15.x，不能是 C:\msys64\ucrt64\bin 的 16.x
```

体检：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\check-duckdb-toolchain.ps1
```

GCC 15 的来历：`niXman/mingw-builds-binaries` 的 `15.2.0-rt_v13-rev1`
（UCRT / posix-seh），与 DuckDB 预编译库**同一构建品牌**（库内版本串
`Built by MinGW-Builds project`）。解压在 `D:\tools\gcc15\mingw64`。

> 为什么不能将就 GCC 16：MSYS2 UCRT64 GCC 16 的 `libstdc++.a` 与
> `libstdc++-6.dll` 都**不含** `__emutls_v._ZSt11__once_call`（GCC 16 用
> native TLS），而 DuckDB 预编译库是 GCC 15 + emulated TLS 构建。上游
> [duckdb-go-bindings#105](https://github.com/duckdb/duckdb-go-bindings/issues/105)
> 同环境确认，官方 **closed as not planned**，建议「用完整 GCC 15」。

## 2. 本次修掉的问题

### 2.1 P0 —— DuckDB 测试随机崩进程（堆损坏）

**现象**：包级 `FAIL <pkg>` 却没有 `--- FAIL: TestXxx`；日志里是
`Exception 0xc0000005` 或 `exit status 0xc0000374`（STATUS_HEAP_CORRUPTION）
+ 寄存器 dump；Go 的 `recover` 拦不住，整个测试进程直接死。

**引入时点**：不是回归，是「引入即带病」。

| 层面 | 时间 | 证据 |
|---|---|---|
| 代码/依赖 | 2026-08-22，`5bb2765`（PHASE 14-05） | `git log -S'go-duckdb' -- go.mod` 全程只有这一条，此后从未升降 |
| 编译环境 | 同一天 08:03 | `C:\msys64\var\log\pacman.log`：`installed mingw-w64-ucrt-x86_64-gcc (16.1.0-5)` |

**根因链**（都有实测支撑，不是推断）：

1. 裸驱动最小复现（不经本仓库任何封装）：`NewConnector(:memory:)` +
   `Appender` 100k 行 → **8 次运行崩 4 次**；`SET threads=1` 无效；
   连 `TestDuckDBBootQueries` 这种最轻的用例也崩（0.4 s）。→ 与业务代码无关。
2. 旧库 `bindings v0.1.21` 的归档内**混编**：`libduckdb_static.a` 是老 GCC
   构建，`zstd` / `icu_extension` 却标着 `GCC: (Rev5, Built by MSYS2 project)`
   （GCC 16），还自带一个 `emutls_shim.o` 手补符号 → 链接侥幸通过，运行期
   一个二进制里两套 C++ 运行时 → 随机堆损坏。
3. `bindings ≥ v0.1.22`（含 v0.1.18 / v0.1.24 / v0.10505 / v0.20000）由
   MinGW-Builds（GCC 15 + emulated TLS）干净构建，引用
   `__emutls_v._ZSt11__once_call`，而 GCC 16 侧没有该符号 → **链接期直接失败**。
4. 反过来用 GCC 15 编 v0.1.21 会撞 `multiple definition`（它的
   `emutls_shim.o` 与 GCC 15 的 libstdc++ 冲突）——这就是 shim 的来路。

**修复**（commit `154fcdb`）：

| 项 | 变更 |
|---|---|
| 主依赖 | `marcboeker/go-duckdb/v2 v2.4.3` → `duckdb/duckdb-go/v2 v2.10505.0`（= DuckDB 1.5.6，官方驱动，无 shim） |
| 源码 | **只改 6 个文件的 import 路径**，`NewConnector` / `NewAppender` / `NewAppenderFromConn` 签名不变，业务代码零改动 |
| 工具链 | GCC 15.2.0（见 §1） |

**验证**：`go test ./internal/duckdb/ -count=1` **连跑 10 次全绿**（修复前
8 次崩 4 次）；`./internal/data/`、`./internal/kpi/...` 全绿；`cmd/server`
链接通过。

**回滚方式**（万一要退）：`git revert 154fcdb` —— 但会回到 GCC 16 混编状态，
必须同时把 `CC/CXX/PATH` 指回 `C:\msys64\ucrt64\bin`，且**接受随机崩进程**。
不建议回滚，真正想退就用 `duckdb_use_lib` 动态库路线（见文档第 4 节 C，不推荐）。

### 2.2 P1 —— `kpi/wsl` 三条集成用例（DuckDB 1.5 独占锁）

### 3.2 跨 chunk 模板重组（待办 11.4）

笔记按 4KB 分片入向量库，一份取数模板会被切成 2-3 段（`030_承保清单` 末尾
`'2025'che` 残片就是同一成因）。单段抽不出完整 SQL 时 `BestTemplate` 返回
`ok=false`，guard 只能 skip —— 等于该请求**没有本体校验**。

实现：`chunkTemplateCandidates` 先给每条 chunk 各自文本，再把「同一来源 +
chunk id **严格相邻**」的连续段拼接（原样相接 / 补换行两种变体），
`guardOperationalSQL` 遍历这些候选文本。

**只在 id 严格相邻时合并**：命中是 top-K 子集，id 不连续说明中间那段没进
prompt，硬拼等于把两份不同模板缝在一起。

测试：`internal/server/guard_test.go` 新增两条 —— 相邻分片能拦住谓词字段改动
（R3）、不相邻分片仍 fail-open。

### 3.3 工具链体检脚本

[scripts/check-duckdb-toolchain.ps1](scripts/check-duckdb-toolchain.ps1)：
纯 ASCII（PS 5.1 读无 BOM 的 UTF-8 会按 ANSI 解析，中文会炸）、检查

### 4.3 【P3 · ✅ 已修 2026-11-11（bc5dfcc）】9 条语料 SQL 解析失败

> 下午会话核查更正：这 9 条**不是**「语料含非法 SQL 样本」，而是被
> `ExtractTemplates` 误抓的**非 SQL 内容**（MongoDB shell/JS ×3、FineBI
> shell 命令、定时任务模板表达式、MySQL DDL 片段 ×3、4KB 分片截断的 SQL
> 残片）。原「修语料不改解析器」路线不可行（改围栏没用——解析器不看
> 语言标注；删正文会破坏知识库）。经拍板改为解析器最小改：fence 语言
> 感知（显式非 SQL 标注不提取、且抑制 bareStatement 兜底）+ 语料 8 个
> 文件围栏标注修正。skipped 9→0，可解析 124 条与基线完全一致。
> 以下为原始记录：

`sqlguard-columns` 扫描 202 个 md 时有 9 条 SQL 块 `Shape.Ok=false`（语料自身
含非法样本：`to_date('2026-06-31')`、`dd<=202501231`、`DATE(2025-09-01)`、
全角括号、未闭合引号）。这是 DESIGN §2 已知的历史数据缺陷，guard 对它们
fail-open。**不建议**为它们改解析器；若要提升覆盖率，应修语料。

### 4.4 【环境 · 已绕过】GitHub release 下载被中间代理拦

**症状**：`curl` 直连 `github.com/.../releases/download/...` 得到
`HTTP=404 SIZE=19`（假 404，API 元数据却正常）；`winget` 报 `0x80072f0d`；

**可用通道**：`https://gh-proxy.com/<原始 GitHub URL>`（实测 8.7 MB/s）；
`ghfast.top` 次之（0.4 MB/s）。`ghproxy.net` / `hub.gitmirror.com` /
`github.moeyy.xyz` / `gh.llkk.cc` 本次不可用。

**另**：Windows 自带 `tar.exe`（bsdtar）能直接解 `.7z`，不需要装 7-Zip。

### 4.5 【环境 · 已规避】PowerShell 5.1 与 UTF-8 无 BOM 脚本

`write` 出来的 `.ps1` 是无 BOM UTF-8，PS 5.1 按 ANSI 读 → 中文乱码 → 引号配对
失败 → `TerminatorExpectedAtEndOfString`。**结论：仓库里的 `.ps1` 一律写纯
ASCII**（`check-duckdb-toolchain.ps1` 已按此改）。

`Out-File -Encoding utf8` 会带 BOM，而 Bash 的 `>` 在 PS 里写 UTF-16 —— 读日志
时若见到 `ERR_INVALID_ENCODING`，就是撞到这个。
