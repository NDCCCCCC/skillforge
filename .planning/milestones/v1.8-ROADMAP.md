# SkillForge v1.8 Roadmap — Ingest Integrity & Ontology into Production

## Milestone Goal

把三轮实证分析（2026-11-23，摄取链路 / 本体消费面 / 来源标注）+ 用户追加需求（摄取过程可视化与任意步骤重试）落成生产路径：

1. **摄取完整性**：修复摄取链路的三个数据完整性断点——上传文档重启蒸发（Milvus 整 tier purge / embedded 缓存 key 均不含 Insert 行）、两套分块器不一致（`chunkBody` vs `splitBody`）、文档无生命周期（无 doc_id / 无删除 / 新旧版本并存）。
2. **摄取流水线可视化与步骤重试**：新增知识的过程在前端清楚展现每一步（解析 → 分块 → 向量化 → 入向量库 → ECL 实体抽取 → KG 加载），任意步骤可单独重试——把 Phase 39 ECL 管线 tab 已验证的「五段状态机 + 失败表 + retry」模式推广到整个摄取链路。
3. **本体进生产路径**：实体锚定检索（接线 Phase 41 hybrid pipeline）、grounding 实体校验（替换 no-op stub）、ECL 自动触发。v1.7 诚实清单条目「KG 实体未进 chat 检索」闭合。
4. **来源标注（Provenance）**：每个引用自报来源通道（vector / graph / hybrid），检索先广播通道分布，KG 缺席明确缺席，拒答交代查过什么。本体 ROI 第一次可度量。

核心不变量（必须贯穿全部 phase）：

> **Citation 的语义是"这段原文逐字支撑这个论断"（grounding，D2-03 verbatim）；来源标注的语义是"这个 chunk 通过什么通道被找到"（provenance）。两者正交——本体只引导检索，不直接制造引用。**

## Phase Details

### Phase 53: 摄取链路完整性

**Goal**: 消灭摄取链路三个数据完整性断点。此后上传文档与目录文档同源同命：落盘即事实、重灌不蒸发、切块同策略、生命周期可管。
**Depends on**: Nothing（v1.8 首个 phase）
**Requirements**: ING-01, ING-02, ING-03
**Success Criteria** (what must be TRUE):

  1. `POST /api/admin/kb/:slug/upload` 成功后在 `knowledge/<slug>/` 出现落盘文件（frontmatter 记原始 sha256/mime/uploaded_at；原始二进制存 `data/uploads/`）；重启后 `seedDocs` 的整 tier purge 重灌把它按目录文档扫回来，embedded 缓存 corpusHash 将其计入——**无静默丢失路径**（重启前后 `GET /api/knowledge/chunk/:id` 集合一致）。
  2. `chunkBody` 退役，`UploadIndex` 改用与 `Index` 同一套 `buildSplitter`/`splitBody`；跨路径等价性测试（同文档两路径 chunk 序列逐字节一致）进 `verify-phase-53.sh` 常驻门。
  3. Document 新增 doc_id / chunk_index / content_hash 三字段 + 文档级 upsert/delete：同 doc_id 重传 = 按 expr 删旧插新（content_hash 未变的 chunk 跳过重嵌——LlamaIndex refresh 增量模式）；`DELETE /api/admin/kb/:slug/docs/:doc_id` 存在且有测试。
  4. `bash verify-phase-53.sh` exit 0。

### Phase 54: 摄取流水线后端（状态机 + staging + 重试）

**Goal**: 摄取从同步 HTTP 内联转为异步 job，每一步可观测、可单独重试。参照 Dify Knowledge Pipeline 的节点模型（Extract/Transform{Parse,Enrich,Chunk,Embed}/Load 各为节点）与既有 ECL 五段状态机（LOCKED stage 契约沿用不改名）。
**Depends on**: Phase 53（落盘先落，staging 才有事实可存；doc_id upsert 是 vector_insert 幂等重试的前提）
**Requirements**: ING-04, ING-05（后端契约部分）, ONT-01
**Success Criteria** (what must be TRUE):

  1. job 模型：`POST upload` 返回 job_id；`GET /api/admin/ingest/jobs/:id` 返回 step 级状态机 `parse → chunk → embed → vector_insert → ecl_merge → ecl_extract → ecl_kg_load → ecl_milvus_load`，每步带 `pending/running/done/failed/skipped` + 耗时 + 失败原因（failure reason 是一等字段——Dify 教训：失败原因必须在文档/任务列表页可见，不是藏在日志）。
  2. staging 持久化：每步产物落盘可定位（复用 `internal/data` 的 staging/datasets 两阶段模式）——这是任意步骤重试的前提；重试语义分步：parse/chunk 重试 = 纯函数从头跑（幂等）；embed 重试 = 只重嵌失败 chunk（per-chunk 状态）；vector_insert 重试 = Phase 53 doc_id upsert（天然幂等）；ecl_* 重试 = 复用既有 per-note retry ×3 与 `ecl_failures` dead-letter。
  3. `POST /api/admin/ingest/jobs/:id/steps/:step/retry` 存在；RAGFlow 教训落为交互约束：failed 步骤的 retry 先隐式 stop 上游残留再重跑，API 返回首个 task 错误而非泛化失败。
  4. ECL 自动触发：摄取成功 → ECL 异步入队（D-Run-01 的 admin 手动入口保留为叠加）；ECL 失败 WARN + dead-letter，不影响向量可检索（增强品失败语义）；embed 阶段批处理/并发（worker-pool ≤3 同 ECL extract 纪律）。
  5. **step 表 schema**（Dify/RAGFlow 源码级模式）：`ingest_step` 行 = `(run_id, step, status, attempt, started_at, completed_at, error, artifact_ref)`——每步独立状态+完成时间戳落库（时间戳差本身就是进度条数据，前端零推送可渲染）；`artifact_ref` 持久化每步产物定位（parse→parsed_text_ref；chunk→chunk_id 列表，RAGFlow `Task.chunk_ids` 模式；embed→embedding 缓存唯一键 `(model, content_hash)`——Dify `Embedding(model_name,hash)` 模式，重试不重算未变 chunk；milvus_load→写入 PK 集合，重试前按上次 artifact_ref 先 purge 残留防写放大）。
  6. **错误分流重试**（Temporal `NonRetryableErrorTypes` / Azure transient vs permanent 模式）：瞬时错误（embed API 429/网络）自动退避重试 ×3；确定性错误（解析失败、KG schema 错误）直接 dead-letter 等人工，不自动重试。重试 API 仅 `failed` 步骤可触发，续跑从上游最近成功步骤的 artifact_ref 开始，下游步骤自动置 `stale`（对应 Dify `re_segment`）。
  7. **job 态与 item 态分离**（Bedrock "COMPLETE 但 N 文档失败" 模式 / Unstructured `failed-files` 端点）：job 不因个别 chunk 失败而整体标败，失败明细单独可查；部分成功显式化。
  8. **崩溃恢复**：进程重启后 running 状态卡死需恢复扫描（RAGFlow run 标志 + 重启重扫模式）；`HasUploadBySHA256` 查错 fail-closed 化；audit `ParserVersion` 取 parser registry 真实版本。
  9. `bash verify-phase-54.sh` exit 0。

### Phase 55: 摄取流水线前端视图

**Goal**: 新增知识的过程在前端清楚可见——用户原话"新增知识的过程要清楚地展现进入向量库和本体识别等等步骤，可以在任意步骤重试"。参照 Dify Knowledge Pipeline 的 Test Run + Variable Inspect（逐步执行、节点输入输出可查看）与文档列表的状态悬停-失败原因-点击 Retry 模式。
**Depends on**: Phase 54（后端 step 契约先定）
**Requirements**: ING-05（前端呈现部分）
**Success Criteria** (what must be TRUE):

  1. `55-UI-SPEC` 先行（Standards：涉 web 先产 UI-SPEC）：步骤时间线组件（八步流水线，每步状态徽章 + 耗时 + 失败原因）+ 步骤点击展开该步输入/输出摘要（Dify Variable Inspect 模式：parse 产物字数、chunk 数、embed 向量数、入库行数、抽取实体数）+ failed 步骤的重试按钮。
  2. 上传动作与流水线视图的入口打通：上传后自动跳转/浮出该 job 的流水线视图；轮询沿用 ECL tab 的 2s/10s 自续模式（既有 hook 复用）。
  3. ECL 四段（ecl_merge/ecl_extract/ecl_kg_load/ecl_milvus_load）沿用 39-UI-SPEC 既有 stage 哨兵契约（LOCKED，不得改名）；新增四段（parse/chunk/embed/vector_insert）为扩展哨兵，同一时间线统一呈现。
  3b. **双层状态**（Dify `display_status` 派生模式）：机内存 8 态细粒度，前端只展示 4-5 态派生状态（queued/running/error/done），避免用户看到内部抖动；多文档批量上传时呈现「文档 × 步骤」矩阵格子着色（Airflow Grid view 模式）；`progress_msg` 追加式日志流可展开（RAGFlow 模式）。
  4. 重试交互与审计：每次步骤重试产生 audit 行（含重试者/时间/该步前后状态）；重试成功后流水线从该步继续而非整链重跑。
  5. `bash verify-phase-55.sh` exit 0（含 FE 测试段）。

### Phase 56: 操作面板可用性（审批规则 + 右侧检查器）

**Goal**: 修复用户反馈的两个面板体验断裂：左侧审批规则/计划审批规则恒为空（args_hash 精确匹配 + binary scope 无 global + 无 CRUD + 无命中统计 = 规则绝育）；右侧审计/规划/引用/Skill/agent 状态面板"提了但没被正确应用"（组件齐全但写入链路有洞 + 交互触发式可见性差）。
**Depends on**: Nothing（可与 Phase 53/54 并行；依赖其自身的后端小改）
**Requirements**: PANEL-01, PANEL-02, PANEL-03
**Success Criteria** (what must be TRUE):

  1. **审批规则模型升级**（业界互证：LangGraph `interrupt_on` 按工具配置审批、Claude Code 权限系统 `Bash(cmd:*)` 前缀匹配、GitHub Environments 实体级规则页）：`approval_rules` 增加 `match_type`（exact/prefix/template）+ `args_pattern`（参数模板，锁定字段+自由字段）+ scope 三层（session/skill/**global**）+ `expires_at` TTL + `enabled` 开关 + `hit_count`/`last_hit_at` 命中统计 + `origin`（approve_remember/manual/seed）；args_hash 降级为 exact 匹配的索引列不再是唯一键。匹配优先级 session > skill > global，同层 deny 语义保持。
  2. **审批弹窗升级**："Approve + 记住"时让用户选记住范围（仅此参数 exact / 同目标同操作 prefix / 同 tool 模板 template）——不再隐式存一个永不再命中的哈希。
  3. **命中反馈闭环**（面板不恒空的关键）：规则自动放行时在对话流插入系统事件（"已被规则 #N 自动批准"，可点进规则详情）；规则面板显示 hit_count/last_hit_at 列；空状态给引导文案 + "从批准历史建议创建规则"卡片（重复人工批准的 (target, 参数模板) 聚类一键生成）。
  4. **右侧检查器**：以 Langfuse 层级 trace 模式重排信息架构——每次回答挂一棵 step 树（检索命中含各通道分数 → rerank → 工具调用 → 规划步骤），执行中的步骤与已完成步骤视觉区分；引用原文 tab 保持 verbatim span 高亮（D2-03 不变量），增加从引用角标到原文的确定性跳转；audit 行 / plan_todos 行写入洞闭合（默认路径 runner 正常完成时面板非空），空状态给引导而非空白。
  5. `bash verify-phase-56.sh` exit 0（含后端规则匹配测试组 + FE 组件测试）。

### Phase 57: 本体进 chat

**Goal**: 让 989 条三元组第一次参与每一次回答。实体锚定接线 Phase 41 hybrid pipeline（复用不重写），grounding 实体校验替换 no-op stub。完成后 v1.7 诚实清单移除「KG 实体未进 chat 检索」条目。
**Depends on**: Phase 54（ECL 自动触发保证 KG 与语料同步新鲜）
**Requirements**: ONT-02, ONT-03
**Success Criteria** (what must be TRUE):

  1. query 进 chat → rdfs:label 实体字典匹配（162 条 label 现成）→ 命中实体驱动 hybrid pipeline（KG 1-2 hop → Milvus → rerank，GraphRAG local search 的三分上下文模式：KG 邻域 / 关系 / source text units 分型注入）；KG 缺席/损坏 → 明确降级纯向量 + `kg_available:false` + WARN，chat 不阻塞不静默降质。
  2. **正交原则落为代码与测试**（GraphRAG 教训：graph 输出不回链 chunk 则引用不可审计；citation laundering 论文：引用存在≠支撑成立）：graph-only chunk（向量相关性为零）只作 prompt 上下文补充不进 `Citations`；升级为引用必须过向量相关性验证门——测试钉死违规路径。
  3. grounding 实体校验（callbacks/grounding.go 的 no-op stub 退役）：回答实体经授权语料 KG 校验，`entities:{verified,unverified}` 进 verdict payload；unverified 非空 → `review_required=true` 或降 confidence。
  4. `bash verify-phase-57.sh` exit 0。

### Phase 58: 来源标注 wire

**Goal**: 每个引用自报来源通道（参照 Azure agentic retrieval 的 per-citation `activitySource` 溯源与 Anthropic Citations 的可选字段挂载模式）；检索完成先广播通道分布，拒答交代查过什么。副产品：本体 ROI 第一次可度量。
**Depends on**: Phase 57（打标随实体锚定实现同步，分离做会漏标）
**Requirements**: PROV-01, PROV-02, PROV-03, ROI-01
**Success Criteria** (what must be TRUE):

  1. `retriever.Hit` 加 Origin/ViaEntity/ViaRels 运行时字段（零值=vector，不进 Milvus schema）；`verdict.Citation` 加可选 `origin`（缺省 "vector"）/`via`/`channels[]` 字段——contract test（`TestContractStructuredOutputSchema`）扩展后老 schema 断言全绿（Anthropic 模式：citations key 是 content block 的可选扩展）。
  2. 通道融合按 **chunk_pk 聚合**（不按文本——跨 doc 重复文本会误并）；双通道命中 = `hybrid` 且保留 `channels[]` 原始集合；hybrid 排序加权（RRF k=60 起步，业界 baseline，不硬编码自定义权重）。
  3. 新增 `data-retrieval` SSE 事件（检索完成即发、先于回答生成）：`{channels:{vector,graph,hybrid}, anchor_entities, kg:{available,entities_matched}, degraded}`；KG 探活失败 → `degraded:true` + 全 vector。
  4. FE：`58-UI-SPEC` 先行；citation 角标分型 + 回答头部通道摘要行 + KG 缺席徽标 + 拒答卡带通道统计（"语义搜索 0 命中、本体未识别到相关实体"）。
  5. auditchain 记录每次检索 channels 统计；ROI 三查询（graph/hybrid 占比、带 hybrid 回答的 grounding 通过率、anchor 命中率）出数可查。
  6. `bash verify-phase-58.sh` exit 0。

## Key Design Decisions（执行 agent 必读）

- **D-53-01 单一事实来源**：`knowledge/` 是唯一事实来源，Insert 只是热路径加速。落盘让 purge 重灌从数据丢失变幂等刷新，embedded 缓存 hash、GraphBuilder、docs 列表全部自动生效。
- **D-53-02 分块器唯一**：CJK-aware recursive splitter 是唯一切块器；`chunkBody` 整体退役不保留开关。
- **D-53-03 PK 策略保持自增**：upsert 语义用「按 doc_id expr 删旧插新 + content_hash 增量跳过重嵌」实现（LlamaIndex 删旧插新模式），**不改** Milvus INT64 PK 为确定性派生键（hash64(doc_id,chunk_index) 方案记录在案为备选——好处是 PK 稳定，代价是重建 collection 与 chunk_id wire 契约变动，不在本里程碑）。已知 Milvus 删除异步可见：upsert 后短暂窗口内新旧并存可容忍（与 reseed 写放大同性质）。
- **D-54-01 失败语义刻意不对称**：embedding=必需品 fail-closed（2026-10-21 原则不动）；KG/ECL=增强品失败 WARN + dead-letter 不阻塞。文档写清，不视为矛盾。
- **D-54-02 staging 先于重试**：每步产物落盘可定位是任意步骤重试的前提（复用 internal/data staging 模式）；无 staging 的重试只能整链重跑，不满足需求。
- **D-55-01 ECL stage 契约 LOCKED**：39-UI-SPEC 的 stage 哨兵不改名，新增步骤是扩展不是替换。
- **D-56-01 规则是 policy**：审批规则本质是策略引擎条目（业界：IAM 的 Effect/Action/Condition、Claude Code 的 allow/deny/ask 三态 + scope 四级）——结构化参数+匹配器存储，**hash 只能做索引不能做唯一键**（不可泛化、不可解释"为什么没命中"）。
- **D-56-02 命中必须可见**：auto-approve 无对话流痕迹 = 功能感知形同虚设（反模式清单第一条）。Temporal 教训：审批痕迹要出现在用户工作的地方。
- **D-57-01 正交原则**：本体只引导检索不制造引用；graph-only chunk 过向量验证门才能升级引用；Citation 的 verbatim grounding 不变量（D2-03）不被 provenance 污染。
- **D-57-02 复用 Phase 41 hybrid pipeline**：KG 1-2 hop → Milvus → rerank 骨架已存在，接线生产 chat 路径不重写。rerank 未接线是另一条诚实清单条目，顺带闭合需显式声明否则 out-of-scope。
- **D-58-01 明确缺席**：KG 不可用 → 全 vector + degraded + 前端徽标，不静默降质。
- **D-58-02 wire 只加可选字段**：contract test 钉死的三字段 Citation 不动语义，新字段缺省值=老行为。
