**T-3-AUDIT INVARIANT (checker-enforced):** The audit table is INSERT+SELECT only. ApprovalCard / AuditTimelineTab / ApprovalRulesPanel never UPDATE or DELETE audit rows. ### Color separation contract (HITL semantic, checker-enforced)

- The 4 approval-state colors (green `已批准` / yellow `已过期` / red `已拒绝` / gray `已记忆`) are MUTUALLY EXCLUSIVE per ApprovalCard — one card shows exactly one state color.

### ApprovalCard — store-derived overlay, NOT a message part (HITL-01, HITL-02, HITL-07)

**THIS IS THE CENTRAL UI/UX DISTINCTION OF PHASE 11. ApprovalCard does NOT live in the message stream.**

- **State source:** Zustand `approval` slice (NEW — do NOT touch D14-banished `messages` field). Slice shape:
  ```ts
  interface ApprovalSlice {
    /** Pending approval card; null = no card visible. */
    pending: PendingApproval | null;
    /** Most recent terminal state; persists for the message build-out. */
    terminal: TerminalApproval | null;
    /** Auto-fade banner toast for cross-refresh resume. */
    resumeBanner: ResumeBanner | null;
  }
  ```
  `PendingApproval = { approvalId: string; toolName: string; target: string; frozenArgs: JsonObject; reason: string; createdAt: number; status: 'pending'; expiresAt: number | null }`. `TerminalApproval = { approvalId: string; status: 'approved' | 'denied' | 'expired' | 'auto-passed' | 'failed'; ... }`. `approvalId === tool_call_id` (D11-C4 single identity).
- **Render mount:** Reads from `(s) => s.approval.pending`. When the field is non-null, the card renders. When null, it does not.
- **Render placement:** `chat-column` interior, `position: absolute`, `z-index: 25`. The chat column itself does NOT grow.
- **State transitions (`approval` slice transitions):**
  - `null` → `pending`: triggered by `GET /api/session/:id/approval` returning a pending row (cross-refresh resume) OR by a Yeti-SSE event arriving on the chat pipeline (D11-C3 fail-closed audit INSERT succeeded → Runner emits interrupt).
  - `pending` → `terminal = { approved }`: triggered by `POST /api/session/:id/approval/:approvalId { decision: 'approve' }` returning 200.
  - `pending` → `terminal = { approved, auto_passed: true }`: triggered by `POST` returning `auto_passed: true` (HITL-08 remember rule matched).
  - `pending` → `terminal = { denied }`: triggered by `POST` returning 200 with `{ decision: 'deny', reason: '...' }`.
  - `pending` → `terminal = { expired }`: triggered by `GET /api/session/:id/approval` returning `state: 'expired'` on cross-refresh OR by BE-emitted expire event.
  - `pending` → `terminal = { failed }`: triggered by `POST` returning non-200 OR by audit fail-closed.
- **Card visual states (single source of truth — `approvalId` is the immutable identity across states):**
  - **Pending state** (default): indigo 3px left-border + pending-pulse animation (1.6s ease-in-out cycle, `--color-tool-accent` family); header strip `--color-surface-2` with `StatusBadge` (`待审批`); body card `--color-surface`; FrozenArgs JSON collapsed by default with `展开` toggle.
  - **Edit mode** (HITL-07): toggled by `编辑参数` button. Card body expands to show a `<textarea>` over the FrozenArgs JSON. Confirmation banner `已修改参数，待审批将以新值执行` appears below the title. `取消编辑` button reverses. The edited args ARE the new FrozenArgs sent on POST.
  - **Approved state** (terminal): green 3px left-border (`--color-status-compliant`); header `StatusBadge` `已批准`; body shows the FrozenArgs JSON (read-only) + a one-line `批于 {ts}` meta. Auto-collapses to 1 line after 3s with `已批准` badge only.
  - **Auto-passed state** (terminal, remember rule): gray 3px left-border (`--color-status-unanswered`); header `StatusBadge` `已通过` (NOT 已批准 — the user did not approve this time); body shows `依据：{target} · {args_hash_8chars}` (mono). Persists as single-line.
  - **Denied state** (terminal): red 3px left-border (`--color-status-non-compliant`); header `StatusBadge` `已拒绝`; body shows the reason in italics below. Persists as 2 lines.
  - **Expired state** (terminal, HITL-03): yellow 3px left-border (`--color-status-needs-info`); header `StatusBadge` `已过期`; body shows the explanation `Skill 或 prompt 已变更，无法恢复` + secondary action `重新发起` button. The 重新发起 button re-fills the composer with the original query and re-sends.
  - **Failed state** (terminal, D11-C3 fail-closed): error red border (`--color-status-error`); header `StatusBadge` `失败`; body shows the failure reason. Approve/deny buttons HIDDEN (fail-closed). Only the audit-fail-closed banner copy displays.
- **Interaction:**
  - `批准一次` button: triggers `POST /api/session/:id/approval/:approvalId { decision: 'approve', frozenArgs: <current args, edited or original> }`. UI shows `批准一次...` + spinner during the request.
  - `批准并记住` button: same POST + extra `scope: 'session' | 'skill'` field. UI shows scope radio (default `session`); the radio is REQUIRED to be selected before POST (the user's intent is to remember, so they must pick the scope).

  - `取消` (in deny prompt): collapses the prompt without action.
  - `编辑参数` button: enters edit mode. `取消编辑` reverses.
  - `展开` / `收起` toggle: shows/hides the FrozenArgs JSON panel.
  - Keyboard: `Enter` submits approve (when in approve mode); `Esc` denies (when in deny prompt mode).
- **SSE channel purity:** ApprovalCard does NOT introduce new SSE chunk types (D15). The interrupt event arrives via the existing `data-decision` discriminator (extended with `decision: 'interrupted'`). The ApprovalCard visibility is store-driven, not stream-driven.

## Wire Contract (Frontend Layer)

ApprovalCard + AuditTimelineTab + ApprovalRulesPanel use the **existing wire types** as the foundation. Phase 11 introduces ZERO new SSE chunk types. The new `data-decision` extension is a discriminator addition, not a new chunk:

```ts
// Existing D16 discriminator — Phase 11 EXTENDS the decision string union
// (not a new chunk type). The discriminated union still wraps a single
// `type: 'data-decision'` chunk; the new decision strings are:
type DecisionType =
  | 'retrieve'      // existing
  | 'answer'        // existing
  | 'refuse'        // existing
  | 'forced-stop'   // existing
  | 'interrupted'   // NEW (HITL-01) — agent calls write tool, Runner emits interrupt
  | 'tool-resumed'  // NEW (HITL-02) — user approved, Runner resumed
  | 'tool-denied'   // NEW (HITL-02) — user denied, Runner forced_stop
  | 'rule-matched'  // NEW (HITL-08) — remember rule auto-passed
  ;

interface DataDecisionPart {
  type: 'data-decision';
  decision: DecisionType;
  payload?: DecisionPayload; // discriminated union (existing pattern)
}
```

**Field casing:** camelCase, consistent with Phase 4. Snake_case silently dropped by AI SDK v5 parser (Phase 4 invariant).

**Approval GET/POST response shape (HTTP, NOT SSE):**

```ts
interface PendingApprovalRow {
  approvalId: string;       // === tool_call_id (D11-C4)
  toolName: string;         // registered handler name
  target: string;           // "memory:facts" | "review_report"
  frozenArgs: JsonObject;   // private snapshot
  reason: string;           // agent's reason line
  createdAt: number;        // epoch ms
  expiresAt: number | null; // checkpoint expiry
  state: 'active' | 'expired';
  skillVersion: string;     // Skill manifest version
  promptHash: string;       // sha256 of RenderSystemPrompt()
  sessionId: string;
  skillId: string;
}

interface ApprovalRuleRow {
  ruleId: string;           // composite PK base64-encoded
  target: string;
  argsHash: string;         // sha256(frozenArgs)
  skillId: string;
  scope: 'session' | 'skill';
  scopeSessionId: string;   // active session_id OR ""
  createdAt: number;
  lastUsedAt: number | null;
}

interface AuditRow {
  // Mirrors T-3-AUDIT backend schema
  auditId: string;
  ts: number;
  sessionId: string;
  action: 'action_pending_approval' | 'action_approved' | 'action_rejected' | 'action_rule_revoked';
  approvalId?: string;      // For pending/approved/rejected: own ID
  ruleId?: string;          // For rule_revoked: own ID
  toolName: string;
  target: string;
  skillId: string;
  skillVersion: string;
  promptHash: string;
  frozenArgs?: JsonObject;  // For pending_approval: snapshot
  argsHash?: string;        // For approved/rejected/rule_revoked: hash
  decisionReason?: string;  // For rejected: user reason
}
```

**HTTP endpoints (NOT new SSE chunks):**
- `GET /api/session/:id/approval` → returns `PendingApprovalRow | null`
- `POST /api/session/:id/approval/:approvalId` body `{ decision: 'approve' | 'deny', frozenArgs?: JsonObject, scope?: 'session' | 'skill', reason?: string }` → returns `{ status: 'ok', auto_passed?: boolean }` or 4xx error
- `GET /api/session/:id/approval-rules?scope=session|skill` → returns `ApprovalRuleRow[]`
- `DELETE /api/session/:id/approval-rules/:ruleId` → returns `{ status: 'ok' }` (BE also emits `action_rule_revoked` audit row)
- `GET /api/session/:id/audit` → returns `AuditRow[]` (filterable by `action` client-side)
