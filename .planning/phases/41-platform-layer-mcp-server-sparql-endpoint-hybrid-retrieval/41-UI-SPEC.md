# Phase 41 — UI Design Contract

> Visual and interaction contract for Phase 41 `/admin/platform` — SPARQL Playground (CodeMirror 6) + MCP Inspector (tools list + test invoke) + Hybrid 调试面板 (KG expansion + Milvus hit list). This extends the v1.4 **consistency-locking** regime: the existing admin console design language is LOCKED; this phase adds the 11th tab (platform) as a direct structural clone of the Phase 40 governance tab (SubrouteTab + view switcher + three views). Every token, class idiom, and pattern below is inherited from the implemented console (`web/src/components/admin/`) and the approved 40-UI-SPEC — not redesigned. Generated by gsd-ui-researcher.

**Dependency change (exactly one, sanctioned by 41-CONTEXT D-UI-03):** `codemirror` (plain npm package, `^6.x` — planner pins exact latest stable) for the SPARQL Playground query editor. Integration rules:

- **No wrapper library** — mount via a container `ref` + `useEffect`, destroy on unmount (`EditorView.destroy()`).
- Use only the core `@codemirror/view` + `@codemirror/state` + `@codemirror/lang-json` packages (SPARQL accepts JSON body, no full SPARQL syntax needed); optionally `@codemirror/theme-one-dark` for the dark-theme editor surface (matches the admin console palette; if not used, style via theme.css tokens directly on the editor container).
- No additional plugins (no autocomplete, no lint, no search — minimal viable for a playground).
- Vitest: the editor component tests assert on container presence + placeholder markup, not EditorView internals — `vi.mock('@codemirror/view')` as needed.
- Editor container: `rounded-md border border-border bg-surface-2 min-h-64 font-mono text-xs`.

Everything else: **zero new tokens, zero new CSS files, no shadcn CLI components.** New files follow the Phase 40 folder pattern: `web/src/components/admin/platform/{PlatformTab.tsx, SparqlPlaygroundView.tsx, McpInspectorView.tsx, HybridDebugView.tsx, platformApi.ts, types.ts}` plus wiring in `AdminDashboard.tsx` + `app-store.ts`.

```typescript
export interface SparqlPattern { s?: string; p?: string; o?: string; limit?: number; offset?: number; filter?: string; }
export interface SparqlResult { s: string; p: string; o: string; provenance?: ProvenanceInfo; }

// HybridResponse: planner defines top-level shape wrapping KG expansion + Milvus hits
```

API calls:

- `sparqlQuery(pattern: SparqlPattern)` → **`POST /api/sparql`** (D-SPARQL-01; name PINNED in 41-CONTEXT canonical refs); body = `SparqlPattern` JSON; `X-Skill-Name` header set from the skill selector (or admin baseline if none selected).

- `fetchMcpTools()` → `GET /api/admin/platform/mcp/tools` → `McpTool[]`.
- `invokeMcpTool(req: McpInvokeRequest)` → **`POST /api/admin/platform/mcp/invoke`** (planner route name; FE test harness for MCP tools — does NOT call stdio subprocess directly).
- `runHybridSearch(query: HybridQuery)` → **`POST /api/admin/platform/hybrid/search`** (planner route name); body = `HybridQuery` JSON; `X-Skill-Name` header same as SPARQL.

All GETs fire on view mount. No polling in any of the three views.

## Interaction Behaviors

### SPARQL query lifecycle

1. Edit pattern in CodeMirror editor (or accept default).
2. Click 「Run Query」 or press Ctrl+Enter in editor.
3. Button disabled during flight; results table replaces with skeleton → data / error.
4. Success: results table + count line. `truncated === true` shows the truncated note.
5. Failure (400/403/500/network): error line 「查询失败：{真实原因}」 with inline retry.
6. 「Clear」 resets editor to default pattern + clears results.

### MCP tool test invocation lifecycle

1. Click 「Test」 on any tool row → `selectedTool = name`; Test Invocation Panel renders below the table.
2. Edit params JSON in the CodeMirror params editor (pre-populated with a skeleton from the tool's `inputSchema`).
3. Click 「Invoke」 → `invokeMcpTool({ tool, params })`.
4. Result area shows loading → JSON output / error.
5. Clicking a different tool's Test button switches `selectedTool` and resets the result area.
6. No 「Test」 confirmation dialog — this is a read-only test harness (D-SPARQL-02: SPARQL endpoint is read-only; MCP tools are query-only in this phase).

### Hybrid search lifecycle

1. Enter query text + set max_hops + rerank toggle.
2. Click 「Search」 or press Enter.
3. Both KG Expansion and Milvus Hits sections show loading state simultaneously.
4. Success: KG subgraph renders + Milvus hit list renders; top-5 reranked rows highlighted.
5. Clicking a KG node fills the detail panel with IRI/tier/provenance info.
6. Failure: both sections show error line 「检索失败：{真实原因}」 with retry.

### Cross-cutting

- No `window.confirm` in this tab (no destructive actions — SPARQL is read-only per D-SPARQL-02; MCP tools are query-only; hybrid is read-only search).
- Fetch errors never blank the view: skeleton → error-line-with-retry trio per section; the view stays interactive.
- No polling anywhere (on-demand debug panel; MCP status is checked on mount only).

## Honesty & Trust-Semantics Rules (console red lines)

1. **SPARQL is read-only.** The endpoint only accepts GET-like pattern queries (D-SPARQL-02); any mutation is out of scope. No INSERT/DELETE controls in the playground.
2. **MCP Inspector is a test harness, not a live terminal.** It calls a backend test endpoint (`/mcp/invoke`), not the actual stdio subprocess. The real MCP stdio server runs as a child of the Go process (`cmd/server/main.go`), not in the browser.
3. **No fake MCP connectivity.** The Inspector shows server status (online/offline) and tool list from the backend registration — it does not attempt to connect to the stdio subprocess directly.
4. **Hybrid recall is a debug view, not a production gate.** The SC-4 recall >= 0.85 is verified by `verify-phase-41.sh` in the hermetic gate; this UI only visualizes the pipeline, not enforce the threshold.
5. **Tier isolation is server-enforced.** All three surfaces (SPARQL / MCP / Hybrid) send `X-Skill-Name` header; the server applies `QueryScoped` (Phase 40 SC-5). FE does no client-side tier filtering.
6. **Errors verbatim.** Server error bodies render as-is after the zh-CN prefix; network failures render 网络错误, never a fabricated status.
7. **No fabricated counts.** Triple counts, tool counts, node/edge counts, and hit scores come from server responses only; omit rather than invent.
