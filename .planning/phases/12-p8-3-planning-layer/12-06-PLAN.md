## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| BE SSE channel → FE real-chat-transport.ts | Server-emit-only (Hertz SSE); clients cannot inject data-plan-trace chunks. The transport parser treats incoming chunks as untrusted JSON but only routes recognized types. |
| PlanTracePart → plan slice store | Reads from useAppStore.planByRunId — the store is the single source of truth. Component does NOT mutate useChat.messages (D14 invariant). |
| localStorage → plan slice hydration | On app mount, hydrate planByRunId from localStorage. Trust boundary: localStorage is local-only; no server trust assumption. Retention redaction: plans older than retention window are purged on hydrate. |
| Synthetic tool-call fallback path | Reads from useChat.messages for write_todos tool-call parts; this is a FALLBACK (Pitfall 6) when data-plan-trace is buffered by AI SDK v5. Authoritative state remains in the plan slice. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-06-1 | Spoofing | data-plan-trace chunk fabrication by client | mitigate | SSE channel is server-emit-only; FE only parses server-originated chunks; no client-side chunk construction |
| T-12-06-2 | Tampering | localStorage XSS via plan content | mitigate | Plan content is LLM-generated (may include skill context); render as text only (no innerHTML); escape via React JSX default escaping |
| T-12-06-3 | Information Disclosure | Plan content cross-session leak | mitigate | planByRunId is keyed by runId (which is session-scoped); cross-session access impossible; plan slice is per-tenant by session |

| T-12-06-6 | Repudiation | Cross-refresh state loss | mitigate | localStorage hydration on app mount; plan slice persists; PlanTracePart restores from store on remount |
| T-12-06-7 | Information Disclosure | Plan content retained beyond retention window | mitigate | Plan slice hydrate-time redaction: plans older than retention window are purged; matches Phase 6 SC-5 retention posture |

**Why D15 lockstep paired commit with 12-02 BE?** D15 lockstep rule (Phase 4) requires Go + TS changes in the same commit / PR. 12-02 ships the Go wire.PlanTracePayload + ValidTypes["data-plan-trace"]; 12-06 ships the TS PlanTracePayload + SkillForgeChunk variant. The constant string "data-plan-trace" is the lock — if BE adds it without TS mirror, D15 alarm fails; vice versa.

**Why plan slice is separate from messages (D14 extension)?** Phase 4 D14 forbids `messages` field in Zustand store — useChat owns the message stream; a Zustand `messages` field would create a dual-source-of-truth. Phase 12 extends D14: plan state is also a separate concern (live updates arrive via SSE, not via useChat message parts as the authoritative source). PlanTracePart reads from the plan slice; useChat messages are ONLY consulted for the synthetic tool-call fallback (Pitfall 6 mitigation).

**Why synthetic tool-call fallback (Pitfall 6)?** AI SDK v5 useChat parser may buffer custom `data-*` chunks until message ends. The tool-call lifecycle parts (`tool-input-*` + `tool-output-available`) ARE rendered live by AI SDK v5 — the tool-call surface is the native live-rendering path. By routing write_todos through both paths, we get robust live rendering even if data-plan-trace is buffered. The plan slice is the authoritative state (synthetic path is a fallback).

**Why localStorage hydration on app mount?** PLAN-02 SC-2 requires cross-refresh persistence: "计划随会话持久化——刷新后计划状态仍在". Zustand's persist middleware handles this transparently. Retention redaction (Phase 6 SC-5) applies on hydrate — plans older than retention window are purged.

## Reference Patterns

- **Phase 11 D14** (Zustand no-messages) — plan slice is independent from `messages`; useChat owns messages, Zustand owns plan.
- **Phase 11 D11-D4** (Left sidebar approval rules pattern) — same Zustand slice pattern for plan rules (12-07 ships the parallel panel).

## Pitfall Mitigations

- **Pitfall 6 (data-plan-trace buffering in AI SDK v5):** Synthetic tool-call fallback path — write_todos is also routed as tool-input-* + tool-output-available; tool-call lifecycle is AI SDK v5 native live-rendering surface. PlanTracePart handles both paths; authoritative state remains in plan slice.
- **Pitfall 7 (D15 wire-type drift):** Paired commit with 12-02 BE; AssertAssignable guard in CI test.
- **D14 extension**: plan slice is separate from messages; useChat.messages consulted ONLY for synthetic tool-call fallback (defensive), NOT as authoritative state.

<risk>
## Top 3 Risks

1. **AI SDK v5 version bump may rename the tool-call lifecycle parts.** The synthetic tool-call fallback depends on `tool-input-available` / `tool-output-available` part names. If a future AI SDK v5.x version renames them, the fallback breaks silently. **Mitigation:** TestTransportSwapWithPlanTracePart asserts the chunk shape; if the SDK breaks the contract, the test fails fast. Acceptable for v0.8.

2. **localStorage size limits (5-10MB typical).** A user with 100+ runs × 50 todos each = 5MB+ plan content; localStorage quota may be exceeded. **Mitigation:** Cap plan slice retention at last 50 runs; older plans auto-purge on hydrate. Acceptable for v0.8.

3. **PlanTracePart render performance with 100+ todos.** Each todo renders an icon + text + animation; 100+ todos may slow the chat-column. **Mitigation:** Virtualize the list via react-window if todos.length > 50; out of scope for 12-06 but recorded for Phase 13+ optimization.
</risk>
