## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| FE → POST /api/run/:id/plan/:approvalId/approve | Untrusted body; ApprovalDecision validated server-side (422 on invalid); reason required for deny (HITL-02); frozen_args edit preserved verbatim (HITL-07). |
| GET /api/run/:id/plan response → PlanReplayView | Read-only; the response shape is the audit truth; the FE renders but does not mutate. |
| DELETE /api/session/:id/approval-rules/:ruleId | Untrusted ruleId; server-side validates the rule belongs to the current session (T-3-SQLI); 404 on unknown ruleId. |
| data-decision{decision:'forced_stop'|'plan-approved'|'plan-denied'} SSE chunks → approval/plan slices | Server-emit-only; FE only parses recognized decision values; unknown values are ignored (defensive). |
| CenterPanel tab → PlanReplayView | Active tab kind drives the rendered component; tabs are local-only (no server trust assumption). |

## Design Rationale

**Why PlanApprovalCard mirrors ApprovalCard verbatim (D11-B2/B3 reuse)?** Phase 11 ApprovalCard already implements 6 visual states + scope radio + edit-before-approve + deny reason validation. PLAN-03 reuses the same UX pattern — the only difference is the endpoint path (/api/run/:id/plan/:approvalId/approve vs /api/session/:id/approval/:approvalId) + the target discriminator ('plan_approve' vs 'memory:facts'/'review_report'). The store slice is shared (approval.byId keyed by approvalId; the target is part of the ApprovalInfo payload).

**Why PlanReplayView fetches GET /api/run/:id/plan instead of reading from plan slice?** The plan slice (12-06) holds the live trace for the ACTIVE run; PlanReplayView renders historical traces for PAST runs (or paused runs). The fetch-from-server pattern is more authoritative than reading from the local store (the local store may have been purged by retention redaction; the server is the source of truth for replay).

**Why PlanRulesPanel reuses the approval_rules endpoint?** D11-D2 single table: approval_rules is shared across all HITL targets (memory:facts / review_report / plan_approve). The endpoint DELETE /api/session/:id/approval-rules/:ruleId takes a ruleId; the server filters by target='plan_approve' for plan-specific rules. No new endpoint.

**Why CenterPanel adds 规划轨迹 between 审计时间线 + 引用原文?** Logical flow: 审计时间线 shows event-level audit rows (approvals, rejections, budget triggers); 规划轨迹 shows run-level plan evolution (todo transitions); 引用原文 shows source chunks. The order matches the agent's reasoning flow (audit → plan → source).

**Why data-decision enum extends with 3 values (P12-L3 + 12-04 + 12-05)?** D16 overload pattern (Phase 3) + D15 wire-type alarm: new discriminator breaks D15 lockstep. New VALUES in existing Decision enum keeps the discriminator count stable. The FE parses the same data-decision chunk; the only addition is a new case in the decision switch.
