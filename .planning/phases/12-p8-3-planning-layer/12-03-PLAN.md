## Design Rationale

**Why reuse `hitl_review_report.go` verbatim (P12-L7)?** Phase 11 D11-CONTEXT §Deferred Ideas explicitly said "Phase 12 PLAN-03 计划确认门 — 复用 HITL Tool 审批模式 + 同 ApprovalDecision schema + 新建 `hitl_plan_approve.go` Tool 文件 + registry 加一行". The deferral scaffold has now activated. P12-L7 zero-schema-divergence means the plan_approve Tool uses the SAME ApprovalDecision struct, audit_writer seam, dual-table snapshot, fail-closed posture — no new schema types, no new audit_writer methods, no new tables. The only additions are: (a) the Tool file, (b) one line in AllowedWriteTargets, (c) one line in hitlHandlers.

**Why Target="plan_approve" but ToolName="plan_approve_review"?** D11-B2 pattern: ToolName is what the LLM emits in function-calling; Target is the policy routing key. "plan_approve" reads as a policy concept (target); "plan_approve_review" reads as an action verb (review the plan). Mirrors review_report_write (Phase 11) + memory_facts_write (Phase 11) — consistent naming.

**Why deny semantics = forced_stop (D16 overload) instead of "agent rewrites and re-submits"?** Phase 11 D11-CONTEXT Claude's Discretion didn't lock the plan-deny semantic. RESEARCH §Open Questions #3 explicitly defers to "P12 discuss-phase with user; defer to Claude's discretion if not asked". Default interpretation: deny = the current plan is rejected; the LLM can rewrite + re-submit by issuing another plan_approve call (which the budget gate caps via MaxIteration). The "forced_stop" framing is for the DATA stream — the user sees the plan was denied; the agent either rewrites or aborts. The D16 overload emits data-decision{decision:"forced_stop", reason:"plan denied"} so the UI can render a clear "plan denied" state without inventing a new discriminator.

**Why keep action="action_pending_approval" (no new enum)?** Plan_approve rows are distinguished by Target="plan_approve". The audit table has a TEXT column for action; new enum values would require a migration OR a discriminated-string convention. By reusing action="action_pending_approval" + Target discriminator, the audit chain remains uniform and the AuditTimelineTab can filter on Target for plan_approve rows. Simpler + zero migration.
