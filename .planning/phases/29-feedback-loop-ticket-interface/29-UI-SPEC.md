## Component Inventory

### 1. FeedbackRow (modify: `web/src/components/chat/parts/FeedbackRow.tsx`)

**Props change:** `messageId: string` → `turnId: number | null, votedVerdict: Vote | null` (server truth via `data-turn` part). `messageId` remains only as `data-message-id` for tests/keys — never sent to the API (Pitfall 7).

**Vote state machine (server-driven lock, D-29-02/04):**

| State | UI |
|-------|----|
| idle | all 3 pills enabled, `aria-pressed={false}` |
| submitting | clicked pill shows disabled + spinner-free opacity-60; others disabled |
| recorded (201/200 `recorded`) | voted pill → `.feedback-row-btn-active`, others `disabled`; success toast |
| already_recorded (200) | server-returned verdict rendered as active pill (identical visual — idempotent replay is not an error); info toast 「该消息已反馈过：{verdict}」 |
| failure (network/5xx) | **pills re-enabled, no lock** (D-29-04); error toast with real reason |
| turnId null | all pills + ticket trigger disabled + honest title |

**outdated comment box (D-29-06):** selecting 报告知识过时 expands a 1-row textarea (可空). Submitting the vote sends `comment` verbatim (may be empty). Box collapses after lock; the locked pill keeps an aria-label carrying 「已附说明」 when a comment was stored. No length counter UI; max length enforced server-side.

**Ticket form (D-29-13):** 点击 创建工单 toggles an inline panel (NOT a modal, NOT a separate page):
- textarea `问题描述（必填）`, prefilled with the message's plain text truncated to 200 chars (editable)
- reference strip (read-only, mono, 12px): 会话 {session 短 id} · 轮次 #{turnId} · 引用 chunk ids as chips; refusal turns show 「无引用」
- 提交工单 = `Button` variant `default` size `sm`, disabled while description is empty or submitting
- 收起 = ghost, collapses the panel (draft text preserved until unmount)

**Ticket result states (inline under the form, D-29-14 honesty):**

| dispatch_status | Inline result copy |
|-----------------|--------------------|
| `none` | ✓ 工单已受理 · TKT-{n} — 未配置外发渠道，工单已留档 |
| `queued` | ✓ 工单已受理 · TKT-{n} — 正在排队外发 |
| `already_exists` | 该消息已建过工单 · TKT-{n} |
| request failure | inline error line + error toast; form stays open, editable, resubmittable |

After a successful submit the form collapses to the result line; the 创建工单 trigger becomes disabled with label 已建单.

### 2. SfToastViewport (new: `web/src/components/layout/SfToast.tsx`)

Owns BOTH the window listener and the viewport, so `/admin` (early-returned in App.tsx) still gets toasts.
- Listener: `window.addEventListener('sf-toast', …)` — the wizard-success precedent (App.tsx:301-309), but implemented inside this component and rendered in all three App branches (chat / eval) plus once inside `AdminDashboard`'s root div.
- Event contract: `CustomEvent('sf-toast', { detail: { kind: 'success' \| 'error' \| 'info', message: string } })`. Lenient mapping for legacy dispatchers: `'error'` → error, `'success'`/`'compliant'` → success, anything else → info (SessionDrawer.tsx:170 dispatches `kind:'error'` — works verbatim).
- Single slot, latest-wins; timer resets per message; auto-dismiss 4000ms (success/info), 6000ms (error); close button `data-testid="sf-toast-close"` `aria-label="关闭"`.
- `role="status"` `aria-live="polite"` `data-testid="sf-toast"`; variant classes: success `border-status-compliant/40 text-status-compliant`, error `border-status-non-compliant/40 text-status-non-compliant`, info `border-border text-text`.

## Interaction Behaviors

### Vote lifecycle
1. FE POST `/api/feedback` `{session_id, turn_id, verdict, comment?}` — `turn_id` is the server `session_turn.id`, strictly a number.
2. Response drives the lock (state machine above). FE local state is a **cache, not truth** — history restore (`voted_verdict` in `historyEntry`) can override it on session load.
3. Toast always fires with the server-verified outcome; failure toasts carry the real reason (HTTP status text / network message) and the row stays retryable.

### Ticket lifecycle
1. POST `/api/tickets` `{session_id, turn_id, description}` → 201 `{ticket_number, dispatch_status}` returns immediately (dispatch is async best-effort, TKT-04 — the UI never waits on or polls it).
2. The three dispatch states render exactly the §Component-1 copy. `queued` never upgrades in-place this phase (admin ticket list is deferred) — the inline line is terminal for the session view.

### Admin disposition
1. Single click → busy → refetch list from server truth (server response is the only state source — KnowledgeBaseList `loadBases` pattern).
2. Success toast names the closed-entry count so the batch effect of D-29-08 is never silent.

### Dimension / range / granularity switches
Client-side state per panel (component-local `useState`, no zustand fields — matches DocUpload/KnowledgeBaseList localism); switching re-fetches with new query params; no caching layer.

## Honesty & Trust-Semantics Rules (FBK-05 — UI red lines)

1. **Never imply automatic trust mutation.** Forbidden strings anywhere in Phase 29 UI/copy: 「已降权」「已下线」「已从知识库移除」「已自动更新知识库」. Vote copy says 记录/复核; disposition copy says 状态标记/审计.
2. **outdated ≠ fixed.** The outdated toast promises 人工复核 only. The 已更新 disposition toast names the closed-entry count, never 「知识已更新」.
3. **Ticket honesty.** provider=`none` renders 未配置外发渠道，工单已留档 — never 「已发送至工单系统」. Dispatch failures are audit-visible server-side; the FE never fabricates a delivery status it was not told.
4. **Server-driven locks.** Every locked/disabled state is derived from a server response or `historyEntry`, never from optimistic FE truth (CONTEXT specifics).
5. **No fake capabilities.** No buttons that 404: no ticket list view, no feedback delete, no disposition undo, no trust controls.
