- Define `func dedupAndSortCitations(citations []verdict.Citation) []verdict.Citation`:
  ```
  if len(citations) == 0 {
      return []verdict.Citation{}
  }
  // First-wins dedup by (ChunkID, Span) — deterministic
  seen := make(map[string]bool, len(citations))
  var deduped []verdict.Citation
  for _, c := range citations {
      key := c.ChunkID + "\x00" + c.Span // null-byte separator avoids chunk_id+span key collision
      if !seen[key] {
          seen[key] = true
          deduped = append(deduped, c)
      }
  }
  // Sort by (ChunkID ASC, Span ASC) for byte-identity contract
  sort.SliceStable(deduped, func(i, j int) bool {
      if deduped[i].ChunkID != deduped[j].ChunkID {
          return deduped[i].ChunkID < deduped[j].ChunkID
      }
      return deduped[i].Span < deduped[j].Span
  })
  return deduped
  ```

## Design Rationale

**Why a PURE FUNCTION for the merge?** FAN-03 SC-3 demands determinism — the same group of sub-agent results must produce byte-identical output across 10 calls. A pure function is the canonical mechanism: no audit (which writes to the database), no SSE (which writes to the wire), no map iteration (which is randomized), no time.Now (which is wall-clock-dependent), no goroutines (which introduce scheduling non-determinism). The 10× contract test is the regression lock — if any future executor introduces side effects or randomization, the test fails immediately.

**Why sort first, then bucket?** Two-step ordering is critical for determinism: sort.SliceStable produces a fixed ordering based on (ID ASC) regardless of input permutation; the subsequent bucket loop iterates the SORTED slice (NOT a map). This is Pitfall 3's exact mitigation: the merge function NEVER iterates a map; the helper `dedupAndSortCitations` uses a local map (allowed because its OUTPUT is a sorted slice), but the merge function's outer loops are slice-iteration only.

**Why conservative partial-failure merge (P13-L5)?** D2-14 posture from Phase 2: when the LLM emits a refusal, the merged verdict downgrades to `needs_input` + confidence 0. Phase 13 extends this to FAULTED sub-agents — a panic / LLM timeout / retriever backend stall is logically equivalent to a refusal (the sub-agent couldn't produce a grounded answer). The conservative posture is: "I cannot confirm; please rephrase or provide more context" — never "I confirm" when one sub-agent failed. This is the safety mechanism against partial-information false positives in fan-out scenarios.

**Why min-confidence aggregation (not mean, not max)?** Min is conservative — if any sub-agent has low confidence (0.85), the merged verdict reflects that. Mean would smooth over the low-confidence signal; max would hide the low-confidence sub-agent entirely. Min preserves the "weakest link" property: the merged verdict is only as strong as the weakest grounded sub-agent. Combined with `ReviewRequired = minConfidence < 0.9` per D2-13 calibration, this gates human review when ANY sub-agent produces a low-confidence claim.

**Why REUSE `verdict.ComplianceStatus` instead of a new `MergeStatus` type?** Single-vertex Runs and fan-out Runs produce the same wire-shape verdict. The FE renderer (`RightChat.tsx` verdict card) doesn't need to distinguish — both end as either "confirmed" or "needs_input". A new type would explode the wire-shape and force FE to maintain two render paths. REUSE is the load-bearing invariant for FAN-04 cross-archetype consistency.

**Why JSON tag order = sort key order?** The 10× byte-identity contract test uses `bytes.Equal(json.Marshal(...))` — JSON tag order affects the marshaled output. By declaring JSON tags in the canonical sort order (id → status → sub_query → verdict → refusal → confidence → citations), the test naturally produces the canonical byte sequence regardless of input permutation. If a future developer adds a field BEFORE `id` (sort key 1), the test breaks and the regression lock fires.
