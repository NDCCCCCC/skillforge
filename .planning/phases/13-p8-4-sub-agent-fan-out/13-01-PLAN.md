## Design Rationale

**Why a new archetype `orchestrator` instead of a special Tool on DeepAgent?** Phase 12 P12-L2 hardened `WithoutGeneralSubAgent: true` to prevent sub-agent injection. Re-enabling it for Phase 13 would require DeepAgent's auto-injected `task` tool to enforce tier-closure + audit RunPath + per-sub-agent grounding + structural read-only — far too many cross-cutting concerns packed into one tool call. A dedicated `FanOutOrchestrator` archetype makes the 5-step pipeline explicit + testable + auditable. DeepAgent's `task` tool remains disabled (P12-L2), preserving the boundary.

**Why Option B (manual `errgroup`) instead of `adk.NewParallelAgent`?** The Phase 13 RESEARCH §Pitfall 1 proves that `NewParallelAgent`'s "full context sharing" (per `forkRunCtx` at `adk/runctx.go:478-508`) directly conflicts with FAN-02's structural tier-closure invariant. Sub-agents built via `NewParallelAgent` inherit parent's `runSession.Values` map — a prompt-injection attack on a sub-agent could expose parent's session state. Option B (manual errgroup + per-Run agent construction) bakes tier-closure into the Tool closure at construction time, making it structurally impossible to expand.

**Why `subManifest.Writes = []` AT CONSTRUCTION in BuildSubAgent, not in `fan_out_dispatch` Tool validation?** The Tool validator (13-01 Task 3) rejects sub-queries with bad tier_filter; the ManifestBuilder enforces non-empty intersection. The structural read-only enforcement happens at the LAST possible point — the BuildSubAgent site — so even if a future caller bypasses the LLM Tool and calls BuildSubAgent directly with a subManifest that has writes, the writes are zeroed. Multiple independent guards prevent drift.

**Why hardcode `SubAgentMaxIteration: 5` + `SubAgentTokenBudget: 20000` instead of config-driven?** P12-L2 precedent: hardcoded budgets eliminate operator drift on a config knob. The acceptance gate in 13-05 measures actual sub-agent cost; if budget is too tight, escalation is an explicit code change + updated test assertion — not a config switch.

**Why a separate `SharedChunkAccumulator` LRU wrapper instead of reusing parent's `*agent.ChunkAccumulator` directly?** Pitfall 6 — N sub-agents × 5 chunks each could grow the accumulator to N×5 = 15+ chunks for a 3-sub-agent fan-out. The LRU cap at 20 prevents unbounded growth while preserving the "small + varied" subset that the citation entailment verifier needs for grounding. Each sub-agent's own retrieved chunks + the parent's seed retrieval co-exist in the LRU; per-sub-agent grounding sees the union but bounded.

**Why `cmd/spike-fanout` is hermetic (no LLM call) in 13-01?** RF-4 (highest uncertainty per RESEARCH) is the structural tier-closure LOGIC — does the closure baking work? — NOT the LLM classifier's correctness. The hermetic spike proves the tier-closure substrate compiles + enforces + is reachable. 13-05's live-mode adds the LLM component for the end-to-end fan-out UAT.
