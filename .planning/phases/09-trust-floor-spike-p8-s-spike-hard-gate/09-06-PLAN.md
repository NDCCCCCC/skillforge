**【planner 裁决 1 — 命令分段 vs 单次合并】** Phase 8 frozen 跑 50 例用 ~15 min；本 plan spike 总共 35 例（25 短 + 10 长），单次合并跑 ≈ 18 min / cost ≈ $1.80。裁定：**单次合并跑**——把 `--category=adversarial,followup` + `--history-length=long` 在同一个 `cmd/spike-history` 进程内跑完（同 costState 累计、同 LLM 会话复用）。命令分段 = 命令 1 `go run ./cmd/spike-history --category=adversarial --out=reports/` → 命令 2 `go run ./cmd/spike-history --category=followup --out=reports/` → 命令 3 `go run ./cmd/spike-history --history-length=long --out=reports/` → 命令 4 `go run ./cmd/spike-history --summarize --out=reports/`。理由：(a) 命令分段让 costState 在每段重置（但每段都设 --cost-limit=5.00 即可），(b) 任何一段失败可以单独重跑（不必从头跑），(c) Plan 09-03 main.go 的成本守卫在 cost 击穿时保留已写入 JSONL，所以分段不影响结果完整性，(d) reports/{adversarial,followup,long}.jsonl 文件名按 --category 自动分发，分段跑更直观。

**【planner 裁决 2 — human-verify 任务用文件级静态检查】** Phase 8 的 live 验证用 `scripts/spiked e2e` + `taskkill + curl` 复跑 SSE。本 plan 的 live 验证 = 4 SC 静态断言：(a) 文件存在性（grep / ls）+ (b) summary.md 关键节存在（grep）+ (c) jsonl schema 字段（python json.load）+ (d) git status 验证 frozen 零改动。**不需要**起 server / 起 UI / 起 chat session。**不需要** chrome-devtools。

**【planner 裁决 3 — reports/ 是否入 git】** reports/ 目录不在 .gitignore 内（与 eval/report.json 同款）。但 spike 产物是**一次性**（与 CI 反复跑的 eval/report.json 不同），不应进 git 历史。裁定：本 plan 把 reports/ 加进 .gitignore（在 SUMMARY 提交同提交），避免后续 plan 误把 spike 数字当作 baseline 引用。**这是本 plan 唯一被批准的 .gitignore 修改**——其他既有 `.gitignore` 规则不动。

**【planner 裁决 4 — 失败 fallback】** live spike 中任何一段失败（API 限流 / Milvus 拒绝 / cost 击穿）的 fallback：(a) `--cost-limit=5.00` 自动断后，可人工 `--cost-limit=20.00` 重跑；(b) Milvus tier-filter 拒绝：检查 MILVUS_ADDRESS env 是否正确；(c) GLM-5.2 限流：sleep 30s 后重试；(d) 任何一段全 fail：立即停止后续段，--summarize 仍可跑（空 JSONL → summary.md 显示 NO-GO 理由「no data」），不让 spike 卡死 Phase 9。
