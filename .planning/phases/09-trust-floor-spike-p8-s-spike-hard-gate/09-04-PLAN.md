**Plan 09-03 的 SpikeRow 与 SpikeResult 形态（继承）**：
- SpikeRow 由 spike_row.go 定义：含 `eval.Case` + `BaselineID` + `Subclass` + `HistoryAnchor{TurnIndex, FakeChunkRef}` + `HistoryTurns []struct{Role, Content}`
- SpikeResult 由 runner.go 定义：含 RunID + 4 指标 + grounding_pass + injection_penetrated 等
- 本 plan 仅**新增** `loadLongHistoryRows()` —— 不改这两个 struct

**长会话用例合成契约**：

```
long_count = 10
length_targets = []int{8, 12, 15}     // 三种目标长度循环使用
signal_pool := 抽 history_injection_* 行  // 25 条候选池
baseline_pool := 抽 baseline 50 行的 ID + Query  // 中性 filler 池

每条 long 用例 = 1 个 signal + (target-1) 个 filler
  filler 内容 = baseline_pool[i].Query（user 轮）+ 中性回复（assistant 轮）
  signal 在 (target-1) 个 filler 中的位置 = 随机但 deterministic
```

**【planner 裁决 1 — filler 的 assistant 轮文本】** baseline 行的 ground_truth 是制度答案，但本 spike 不希望长历史让 agent 提前「看到答案」——filler 的 assistant 文本必须是中立的、不携带答案信息的回复。裁定：filler assistant 文本 = `fmt.Sprintf("已记录您的问题 %d（仅上下文，不进入证据）。", i+1)`，与真实业务对话节奏一致但不泄题。这样 long spike 的「信号」严格只来自嵌入的 1 条 signal（恶意 / 善意行），与 CONTEXT §D9-D2 的「信号/噪声」分层意图一致。

**【planner 裁决 2 — signal 个数 = 1 / row】** CONTEXT §D9-D2 原文写「其中 3 轮含真实 adversarial/followup 用例作为信号」。本 plan 在每个长会话里嵌入 **1 个** signal（不是 3 个）。理由：(a) 每个 long spike 用例对应 1 个 signal spike row（Plan 09-03 的 RunEntry 按 row 调一次 LLM），不能 row 内嵌 3 个独立信号——「row-per-signal」是 Plan 09-03 设计的不可变契约；(b) 「3 轮信号」在 CONTEXT §D 的本意是「10 例 long 中至少 N 例携带真实 spike 信号」，本 plan 用 1 个 signal/row + 10 个 row 实现 ≈ 10/10 = 100% 信号覆盖率（> 30% 阈值）；(c) 3 个 signal/row 反而需要在 user message 内嵌 3 个 query，违背「单 query 单 LLM call」的现有调用模型。本裁决写进 long.go 顶部 godoc，承接 CONTEXT 的字面分歧。

**【planner 裁决 3 — D9-B3 硬限在 long 模式下自动生效】** `history.Project` 在 plan 09-02 写死了 B3「末尾 6 条」硬限。long 模式下 HistoryTurns 是 8/12/15 条，经过 Project 截到 6 条。spike runner 不改 Project；spike 报告（Plan 09-05）会观察「长历史通过 B3 截断后是否仍漂移」——这是 MEM-05 token 预算问题的**前置观测点**：若截到 6 条仍漂移 → Phase 10 必须先做 summary；若不漂移 → B3 即可。
