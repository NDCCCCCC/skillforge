<objective>

Phase 54-02: staging 持久化——每步产物 artifact_ref 可定位（D-54-02：staging 先于重试，无 staging 的重试只能整链重跑）+ embed 缓存 `(model, content_hash)` 唯一键（Dify `Embedding(model_name,hash)` 模式，重试不重算未变 chunk）。

**取舍论证（复用 internal/data staging vs 新建轻量 job store）——结论：目录约定借鉴，机制不搬**。internal/duckdb/staging.go 的两阶段模式核心是**整文件 rename commit**（staging → datasets，同卷 POSIX rename 原子性），适配"一个 dataset = 一个 duckdb 文件"的粗粒度产物；摄取步产物是**多而小**（parsed.txt / chunks.jsonl / pks.json / ecl 计数），且成败簿记在步级（ingest_steps 行），rename-commit 的原子性收益为零、目录约定收益为真。故：产物文件落 `data/ingest/<job_id>/`（与 data/staging、data/datasets 同卷同 git-ignore 语义），注册簿记**不新建文件系统账本，直接用 54-01 的 sqlite ingest_jobs/ingest_steps 表**——JobStore 窄接口已覆盖，避免第三套簿记。embed 缓存是唯一需要新表的部分：向量本体不适合落文件（重试按 hash 随机取用），sqlite `embed_cache(model, content_hash)` 主键即 Dify 唯一键模式；BLOB 存 float32 LE packed（1024 维 ≈ 4KB/chunk，千级 chunk = MB 级，对 skillforge.db 体积与 backup 周期可接受——SQLite 损坏恢复事件已验证 backup 路径可用，体积预算记录在案）。

**合入顺序 01 → 02**（同 wave）：本 plan 对 steps.go 只改 chunk/embed 两个函数体，对 schema.go 只追加 embed_cache DDL——均不触碰 54-01 的段落。

**与 53-03 refresh 的关系**：53-03 的 upsert 在 Insert 前按 content_hash 跳过未变 chunk（省 BGE 调用）；本 plan 把判断**前移到 embed 步**——未变 chunk 在嵌入之前就跳过（LlamaIndex refresh 模式的正确位置），vector_insert 的 skip 集合由 embed 步传入，不再各自为政。

Output: 八步 artifact_ref 全部有值且可定位；同 content_hash 二次摄取零 BGE 调用（embedder 调用计数测试钉死）。
