<objective>

Phase 54-03: 错误分流重试 + 任意步骤重试端点 + 崩溃恢复。三件事（ROADMAP SC 3/6/7/8）：

1. **错误分流**（Temporal `NonRetryableErrorTypes` / Azure transient vs permanent 模式）：瞬时错误自动退避 ×3，确定性错误直接 dead-letter 等人工，不自动重试——区别只在"重试是否可能改变结局"。内网间歇断联（Milvus/BGE/GLM 历史教训：断线记环境 STOP，不刷分）是 transient 的典型；解析失败重试一万次还是失败，是 deterministic 的典型。
2. **`POST /api/admin/ingest/jobs/:id/steps/:step/retry`**（SC 3，RAGFlow 教训落为交互约束）：仅 failed 步可触发；触发前隐式 stop 上游残留；下游级联置 stale；续跑从该步开始非整链重跑；API 返回该步真实 error 而非泛化失败。
3. **崩溃恢复**（RAGFlow run 标志 + 重启重扫模式）：重启后 running 卡死行恢复扫描；job 态与 item 态分离呈现（Bedrock "COMPLETE 但 N 文档失败" / Unstructured `failed-files` 模式）——job 不因个别 chunk 失败整体标败，失败明细单独可查。

Output: retry.go 分类器 + retry 端点 + stale 级联 + boot 恢复扫描 + failed_items 呈现，全部进测试。

</objective>
