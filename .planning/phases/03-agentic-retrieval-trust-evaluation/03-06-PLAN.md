<objective>
Ship the project's measurement moat (D3-08) as a **Go-native** evaluator — no Python, no Ragas process. Stand up (1) a 50-case synthetic golden set (D3-06) covering the 3 GEVL-05 categories, (2) an `internal/eval` package computing faithfulness / answer_relevancy / context_precision / context_recall via a GLM judge + the existing BGE-M3 embedder, (3) a Go CLI (`cmd/eval/main.go`) that drives the agent over the golden set and writes a JSON report + calibration data, and (4) the calibration that retires the magic 0.3 threshold (D2-15).

**Why Go-native (D6 reversal, decided 2026-08-12):** the original plan imported Python + Ragas as a CLI sidecar. Scope review surfaced that (a) `store.AuditRow` already reserves the 4 metric columns, (b) `embedder.Embedder` (BGE-M3) and `retriever.Search` (scored `Hit`s) are already reusable, so the ONLY net-new work is the 4 metric implementations; (c) the research's own build-vs-buy verdict (03-RESEARCH.md line 132) estimated "~2000 lines to match faithfulness alone" for a FULL reimplementation, but that cost concentrates in the **prompts** — and only **faithfulness**'s claim-extraction prompt is genuinely calibration-sensitive. Decision: port **only** Ragas's faithfulness prompt (Apache-2.0, so the headline number stays industry-comparable — "Ragas 口径"); author simple Go judge prompts for the other 3 metrics; keep the whole stack single-language. This eliminates the T-3-SC supply-chain checkpoint (no PyPI audit), drops the `ragas`/`langchain-openai` dependency tree, and avoids the ragas 0.1.21 ↔ Python 3.13 install friction.

**Output:** new `internal/eval/` package + new `cmd/eval` binary + `eval/` data dir (golden set + report + calibration) + a one-line accessor on `internal/agent` + a focused `UpdateAuditMetrics` on `internal/store` + a godoc touch on `pipeline.go`. Depends on Plan 03-02 (Store + AuditRow) + Plan 03-05 (running agent/server).
</objective>

<metric_design>
How each of the 4 metrics is computed (all via the Judge interface in internal/eval/judge.go):

| Metric | Algorithm | Prompt source |
|--------|-----------|---------------|
| **faithfulness** | (1) judge.ExtractClaims(answer) → atomic claims; (2) judge.Entails(claim, retrievedContext) per claim; (3) score = supported/total. Refusal answer (no claims) → 1.0. | **Ragas v0.1.21 ported VERBATIM** (the "Ragas 口径") |
| **answer_relevancy** | (1) judge.GenerateQuestions(answer) → N questions; (2) embed each + original query via BGE-M3; (3) score = mean cosine similarity. | Go-authored (simple "generate 3 plausible questions" prompt) |
| **context_precision** | Per retrieved chunk (rank order): judge.IsChunkRelevant(query, chunk); score = rank-weighted precision. | Go-authored (simple yes/no prompt) |
| **context_recall** | Split ground_truth into statements; per statement judge.IsAttributable(statement, retrievedContext); score = attributable/total. ground_truth="REFUSAL" → 1.0 if system refused else 0. | Go-authored (simple yes/no prompt) |

**Why only faithfulness ports Ragas:** Ragas's calibration-sensitive engineering is concentrated in claim extraction (handles negation, modality, temporal claims, multi-sentence answers). The other 3 metrics are straightforward yes/no judgments where a simple prompt matches Ragas quality. Porting only faithfulness captures ~80% of the validation value at ~20% of a full reimplementation's cost.

**Judge bias (Pitfall 8) counter-measures (unchanged from D3-07):** (a) the deterministic Go grounding floor catches worst-case hallucinations REGARDLESS of judge; (b) human spot-check on a ~10% sample is a documented non-blocking Phase 3 exit criterion (eval/README.md); (c) the JUDGE_MODEL config slot allows Phase 6 cross-evaluation with DeepSeek or another model. Judge temperature=0 (determinism established in spikes 001-003).
</metric_design>
